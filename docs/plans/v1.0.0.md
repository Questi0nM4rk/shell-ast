# v1.0.0 plan — parser + AST walker stabilization

**Status:** draft.
**Author:** session 2026-05-20.
**Scope philosophy:** shell-ast is the parser layer. It parses `bash` / `posix` / `mksh` into a typed discriminated-union AST, exposes traversal primitives (`findCalls`, `findRedirects`, `walk`), unwraps shell wrappers (`sudo` / `doas` / `pkexec` / shells / `eval`), classifies operator effects (`exec`, `pipe`, `fs-write`, `fs-read`, `subshell`), and ships zero-config query helpers (`tokenAfter`, `hasFlag`, `tokensAfter`, `resolvedCmd`). It is the foundation under hook-kit and any future security-tool / linter consumer that needs to understand commands before they run.

1.0 closes the 0.x line. It promises a stable, semver-promised API surface; an exhaustive bug-catalog reconciliation; published performance numbers; cross-runtime CI coverage; and an expanded `GLOBAL_VALUE_FLAGS` table covering the tools modern LLM agents actually invoke. It does NOT add policy semantics, per-tool security knowledge, or anything that belongs upstream in hook-kit / ai-guardrails.

After 1.0, breaking changes follow semver: one minor-version deprecation cycle, then removal at the next major.

---

## What 1.0 promises

1. **Semver islands.** Three stability tiers:
   - **STABLE** (semver-promised): everything re-exported from `src/index.ts`, the `UnwrappedCall` discriminated union shape, the `Effect` union, the typed error taxonomy (`ParseSyntaxError`, `ParseSizeError`, `WasmLoadError`, `WasmRuntimeError`), the `GLOBAL_VALUE_FLAGS` table contents (additions are non-breaking, removals require a major bump), the `ResolveFlagsOptions` shape, the WASM-loading lifecycle (`parse`, `preloadWasm`).
   - **EXPERIMENTAL** (may shift in minor versions with one-release deprecation): any new analytics or convenience helpers added during 1.x.
   - **INTERNAL** (no stability promise): `src/wrappers/registry.ts` schemas, `src/walk.ts` Visitor internals (Visitor type is STABLE, traversal-order guarantees beyond depth-first are INTERNAL), the WASM binary's internal protocol with `wasm_exec.js`.
2. **Discriminated union exhaustiveness.** Adding a new `UnwrappedCall.kind` is a breaking change (major bump). The compiler-error-on-new-variants guarantee that the README advertises stays load-bearing in 1.x.
3. **All 11 catalogued BUGS reconciled.** Every entry in `docs/BUGS.md` has an explicit `**Status:** FIXED in vX.Y.Z` line OR `**Status:** WONTFIX — <reason>`. No bug is left in an ambiguous state.
4. **Deprecation cycle.** Any STABLE removal: one minor-version warning (JSDoc deprecation + runtime `console.warn` once-per-load) before removal at the next major.
5. **Cross-runtime coverage.** CI matrix covers Node ≥18, Node 20, Node 22, Bun (current stable), and `bun build --compile` smoke. Any runtime that ships in CI is supported; runtimes not in CI are best-effort.

## What 1.0 explicitly does NOT ship

- **Per-tool semantic knowledge.** "`gcc -o` writes a file" / "`git push --force` is dangerous" — hook-kit's job. shell-ast surfaces structure; meaning lives upstream.
- **Policy decisions.** No `deny` / `ask` / `warning` here. shell-ast tells you what the command IS; hook-kit decides what to DO about it.
- **Role tags on tokens.** "This arg is a path" / "this arg is a user" — annotation lives in hook-kit, derived from shell-ast's structural output.
- **Schema registries / plugin runtimes.** shell-ast is a library, not a framework.
- **AST `unparse` / roundtrip.** mvdan/sh supports it but exposing here would invite "rewrite-the-command" rules that blur the parser→policy boundary. Defer indefinitely unless a concrete consumer-side use case forces it.
- **Source maps for inline-shell recursion.** When `bash -c '…'` is recursed, inner positions don't map back to outer source. Useful, but lives in the consumer (hook-kit can build this on top using `Word.Pos`); shell-ast won't materialize a new abstraction for it.
- **Non-bash shell families.** No fish, no nushell, no PowerShell. mvdan/sh's coverage (bash / posix / mksh) is the ceiling. Adding a family means a new WASM build per family; out of scope.
- **JS / TS subset for inline `eval`-style strings.** `node -e "..."` / `python -c "..."` are matched at the call level (shell-ast tells you "this is `node -e <STRING>`") — content interpretation lives in the consumer.
- **Browser bundle.** 4.2 MB WASM is fine for CLIs and Node daemons, prohibitive for browsers. If a browser consumer ever materializes, a separate `@questi0nm4rk/shell-ast-browser` package can ship with a TinyGo build.
- **Synchronous parse.** WASM init is fundamentally async. `parse()` stays `Promise<ShellFile>` in 1.x. Consumers wanting sync parse can call `preloadWasm()` at startup and then use the parsed cache.

### M1 — Coverage

#### 1.1 `GLOBAL_VALUE_FLAGS` expansion for common LLM-tool surface

**Goal:** modern LLM agents invoke a wider tool surface than the 6 currently covered (`git`, `docker`, `kubectl`, `make`, `tar`, `xargs`). Each tool with a positional-shifting global flag is a potential rule-bypass for downstream consumers.

**Current state:** 6 tools. Common gaps observed in hook-kit consumer patterns: `aws`, `gcloud`, `az`, `terraform`, `helm`, `kustomize`, `ansible`, `npm`, `pnpm`, `yarn`, `bun`, `pip`, `uv`, `cargo`, `gh`, `glab`.

**Design:** audit each candidate tool, identify its leading value-taking flags from upstream docs, add to `GLOBAL_VALUE_FLAGS` if applicable. For tools where the global-flag surface is large or unstable (cloud CLIs), be conservative — add only the leading positional-shifting ones, not every flag.

#### 1.2 `wrapped-opaque` narrowing audit

**Goal:** every `wrapped-opaque` case is a coverage hole — the consumer can't see what's inside. Audit when `wrapped-opaque` fires; narrow to `wrapped-script` where possible.

**Current state:** `wrapped-opaque` fires for `bash -c $X` (dynamic script), `bash` with no `-c`, and similar shapes where the inner is unresolvable. Some of these may be narrowable.

**Design:**
- Enumerate the call shapes that produce `wrapped-opaque` from `src/wrappers/unwrap.ts`.
- For each, evaluate: is there ANY structural information we could surface? Examples:
  - `bash $SCRIPT_VAR` — opaque, but we know it's `bash`; consumer might want "bash invoked with dynamic first arg" as a signal.
  - `bash -c "$CMD"` — opaque script, but flag `-c` IS present; surface as `wrapped-opaque` with a `reason: "dynamic-script"` field instead of unstructured.
- Decision: extend `wrapped-opaque` with a `reason` discriminator OR leave as-is. Cost/benefit per consumer pain.

**Acceptance:**
- [ ] Audit document (lives in `docs/specs/wrapped-opaque-cases.md`) enumerating every code path that produces `wrapped-opaque`.
- [ ] If `reason` field added: STABLE schema, test coverage per reason variant, README updated.
- [ ] If `reason` deferred: documented in audit doc as "decided WONTFIX for 1.0 because <reason>."

**Risks:** adding the `reason` field changes the `UnwrappedCall` discriminated union shape (additive but observable). Land before semver lock at 1.0.
**Estimate:** S–M (audit) + S–M (implementation if any).

#### 2.2 Parse-cache helper

**Goal:** consumers that parse the same input repeatedly (test corpora, broker-style daemons evaluating identical commands) benefit from an LRU parse cache.

**Current state:** none. Each `parse()` call goes through WASM.

**Design sketch:**

```ts
// src/parse-cache.ts
export function createParseCache(opts?: { maxEntries?: number }): {
  parse(src: string): Promise<ShellFile>;
  clear(): void;
  stats(): { hits: number; misses: number; entries: number };
};
```

LRU keyed by `src` (the raw input string). Default `maxEntries`: 1024. The returned `parse` wraps the top-level `parse`. Stats for observability.

**Acceptance:**
- [ ] Implementation in `src/parse-cache.ts`, re-exported.
- [ ] Tests: hit/miss accounting, LRU eviction, identical-input returns identical AST reference (cached), clear() empties.
- [ ] Documented in README with "when to use" guidance.

**Risks:** consumers mutating the returned `ShellFile` would poison the cache. Mitigation: document "treat returned ASTs as immutable" — if mutation is a real risk, freeze recursively at cache-time (cost) or document the contract (cheaper).
**Estimate:** S.

### M3 — Documentation

#### 3.1 Threat model / capabilities-and-limitations doc

**Goal:** honest, externally-readable document of what shell-ast CAN see and what it CANNOT. Required for any security-critical downstream consumer.

**Current state:** scattered across IDEOLOGY.md, README, BUGS.md. No single canonical doc.

**Design:** new `docs/CAPABILITIES.md`.

Sections:
- **What shell-ast sees:** static structural shape — commands, flags, args, redirects, pipes, subshells, wrappers, env-prefix assignments, here-docs.
- **What shell-ast cannot see:**
  - Runtime variable values (`$VAR` is `DYNAMIC`; we don't track env).
  - Runtime command output (`$(get-command)` returns the command-substitution shape, not the resolved cmd name).
  - Aliases (`alias rm='rm -i'` — the AST sees `rm`, not the aliased form).
  - Functions (function bodies are AST'd; whether a `CallExpr` invokes a user function or a real binary requires consumer-side function-name tracking).
  - Effects of `eval` at runtime (we recurse statically into the literal string passed to `eval`, but only if it's literal).
  - `set -e` / `set -o pipefail` semantics — we parse them, but their EFFECTS on later commands are runtime-only.
- **When wrapper unwrap stops:**
  - `wrapped-opaque` cases (per M1.2 audit).
  - `wrapped-script` with non-literal script (`bash -c "$VAR"`).
  - Chains exceeding consumer depth caps.
- **What `effectOf` classifies vs doesn't:** enumerate the operator set.
- **`GLOBAL_VALUE_FLAGS` coverage:** per-tool table + how to extend via `ResolveFlagsOptions.globalFlags`.

**Acceptance:**
- [ ] `docs/CAPABILITIES.md` exists, all sections covered.
- [ ] Linked from README at the top.
- [ ] Each "cannot see" item has a worked example showing the limitation.

**Estimate:** M.

#### 4.1 WASM size investigation

**Goal:** understand whether 4.2 MB is actually optimal or has slack. Publish the analysis even if no shrink is feasible — consumers stop asking.

**Current state:** 4.2 MB, built via `GOOS=js GOARCH=wasm go build`. No size analysis on record.

**Design:**
- Profile current binary: `wasm-objdump`, `twiggy`, or similar to identify size contributors.
- Evaluate TinyGo as alternative compiler: does it produce smaller WASM? Does mvdan/sh's grammar fit TinyGo's reduced runtime?
- Evaluate gzip/brotli pre-compression: WASM loaders can decompress on the fly (cost: decode latency on cold start).
- Evaluate `wasm-opt -Oz` as a post-processing step.

**Acceptance:**
- [ ] Investigation document in `docs/specs/wasm-size.md` with findings.
- [ ] If feasible shrink: implement in build pipeline; bench to confirm no parse-correctness regression and acceptable latency tradeoff.

## Open questions

1. **`GLOBAL_VALUE_FLAGS` table — ship full M1.1 list or curated subset?** Per the audit risk above, every tool's flag surface shifts. Conservative: ship 5–8 high-value tools at 1.0 (the ones with known consumer pain), defer the rest to 1.x as community PRs land. Aggressive: ship all 16. Conservative is safer for the semver-removals-are-breaking promise.
2. **`wrapped-opaque.reason` field — add or defer?** Adding it is an additive `UnwrappedCall` variant change, observable in TypeScript exhaustiveness checks. Adding at 1.0 means consumers can rely on it; adding in 1.x is a minor breakage. Lean: add at 1.0 if M1.2 surfaces a concrete consumer use case; defer otherwise.
3. **TinyGo investigation — gate or not?** WASM size matters for browsers and embedded use cases that aren't current consumers. Don't gate 1.0 on this; M4.1 produces a doc either way.
4. **Parse cache as built-in or composable add-on?** Built-in (`createParseCache` exported) is more discoverable. Composable (consumer wraps `parse` themselves) is more in line with "library, not framework" ideology. Lean: ship as exported helper but mark EXPERIMENTAL initially.
5. **Should `findCalls` add a `topLevel` option in 1.0?** BUG-006 asked for this; needs verification whether already shipped or still open. If open: ship in 1.0 for parity with `findRedirects({depth: "top"})`.
6. **Coordination with hook-kit 1.0 timeline.** hook-kit's 1.0 plan budgets 12 weeks; shell-ast 1.0 here budgets ~8 weeks. Shell-ast should land first so hook-kit can lock against a stable parser dep. Target: shell-ast 1.0 cut ~2 weeks ahead of hook-kit 1.0.

## Risks

1. **Breaking changes during M1.1 / M1.2.** Expanding `GLOBAL_VALUE_FLAGS` reshapes resolved-flag output for tools currently un-listed. Downstream rules that match on those positions silently shift. Mitigation: every M1.1 PR includes a test against the affected hook-kit consumer behavior; flag in MIGRATION-v1.0.0.md.
2. **WASM-runtime fragility on Bun canary versions.** Bun's WASM loader has had regressions. Mitigation: CI pin Bun to a known-good stable, not canary.
3. **mvdan/sh upstream changes.** The Go side could regress. Mitigation: `go.mod` pins exact version; bumps tracked as deliberate `chore(processor): bump mvdan/sh to vX.Y.Z` commits with regression test added.
4. **Cross-runtime divergence on async semantics.** `preloadWasm` may race differently across Node versions. Mitigation: M2.3 CI matrix catches; add stress test in `tests/wasm.test.ts`.
5. **Scope creep into hook-kit territory.** Pressure to add "just one effect classifier" or "a tiny per-tool helper" — resist. shell-ast is structure; meaning lives in hook-kit. Every potential addition checked against IDEOLOGY before merging.

## Lessons applied from 0.x

- **Discriminated unions force exhaustive consumers.** 1.0 doubles down: every new variant requires a major bump, every removal too. The compiler-error-on-new-variants property is the load-bearing safety net.
- **Honest about limitations.** Per IDEOLOGY §2; M3.1's CAPABILITIES.md is the formalization. Don't silently allow.
- **Primary lens must be complete.** Per IDEOLOGY §11 + BUG-008 postmortem lessons. M1.2 (`wrapped-opaque` audit) is the 1.0 application: don't ship a variant that consumers always have to special-case.
- **Bug → ship the fix, then close the bug entry.** No bugs left in ambiguous state at 1.0; that's the M0.2 reconciliation discipline.
- **Annotated tags only.** Per `qsm-worktrunk` rules.
- **Conventional commits.** Per `git-workflow.md`.
- **CHANGELOG every commit.** `[Unreleased]` updated in the same commit; cut to `1.0.0` heading at release.
